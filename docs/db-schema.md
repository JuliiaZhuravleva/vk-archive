# База данных: PostgreSQL + pgvector

Решение: одна PG-база `vk_archive` вместо связки SQLite+Qdrant — полнотекст
(русский `tsvector`), вектора (pgvector HNSW), реляционка и jsonb в одном месте,
гибридный поиск одним SQL-запросом. DDL: [../db/schema.sql](../db/schema.sql),
запуск: `docker compose -f db/docker-compose.yml up -d` (порт **5433**, только
localhost, данные в `data/db/`).

## Схема (10 таблиц)

```
dialogs 1─* messages 1─* attachments 1─1 voice_transcripts *─1 prompt_batches
   │            │
   │            └─ tsv (FTS russian)          vocab_terms (peer, term, source)
   ├─* dialog_periods (год → промпт)          analyses (peer?, kind, span, md)
   └─* chunks (окно сообщений + vector(1024))
```

| Таблица | Что хранит | Откуда наполняется |
|---|---|---|
| `dialogs` | диалог + доля своих сообщений + флаг `useless` | `index-messages.html`, `participation.json` |
| `messages` | вся переписка целиком (порядка миллиона с лишним), `sent_at`, `is_own`, FTS | парсер HTML (Фаза 1) |
| `attachments` | вложения, локальные пути скачанного | kludges + `media_manifest.jsonl` + `downloads.log.jsonl` |
| `voice_transcripts` | транскрипт, длительность, какой промпт, FTS | `transcription/transcripts/*.{txt,meta.json}` |
| `prompt_batches` | батч: контекст, промпт, источник, new_terms | `transcription/batches/*.json` |
| `vocab_terms` | словарь: ручной посев + автосбор Sonnet | `transcription/vocab/<peer>.md` |
| `dialog_periods` | периоды диалога: описание тем + промпт | `vocab/<peer>-periods.md` |
| `analyses` | LLM-дайджесты, таймлайны, мета-анализ | Фаза 4 (генерация) |
| `chunks` | окна сообщений с эмбеддингами | чанкер (Фаза 3) |

## Ключевые решения

1. **`useless`-флаг на диалоге** — фильтр всей дальнейшей обработки
   (транскрипция, эмбеддинги, дайджесты). примерно каждый пятый диалог; в них 40%
   всех голосовых — экономия сразу.
2. **Транскрипты — отдельная таблица**, а не колонка в messages: у голосового
   свой жизненный цикл (промпт, модель, повторная транскрипция), связь 1:1
   с вложением. Для поиска FTS-индексы на обеих таблицах объединяются UNION'ом.
   **Гоча:** тип вложения — в `kind` (`photo` / `voice` / `other`), а
   `att_type` хранит русскую подпись из архива («Фотография», «Файл»,
   «1 прикреплённое сообщение»). Фильтр `att_type = 'photo'` вернёт ноль
   строк и будет выглядеть как «фотографий в базе нет».
3. **Чанки не заменяют сообщения**: `chunks.text` — склейка окна
   «sender: text» с уже подставленными транскриптами голосовых; границы окна
   привязаны к `vk_msg_id`, так что из найденного чанка всегда можно раскрыть
   исходные сообщения.
4. **Размерность вектора 1024** — по **bge-m3**, выбранной после пилота
   (замеры в README и PLAN.md); смена модели = перезаливка эмбеддингов,
   схема не меняется.
5. **Провенанс везде**: `messages.page_file`, `voice_transcripts.batch_key`,
   `vocab_terms.first_batch` — любой результат можно проследить до сырого HTML.
6. **Markdown-артефакты пайплайна остаются на диске** (vocab, batches,
   транскрипты) — БД их зеркалит для поиска, но источником истины при
   реимпорте служат файлы. Пайплайн транскрипции не зависит от БД.

## Гибридный поиск

Реализован в [`scripts/search.py`](../scripts/search.py): три режима (`fts`,
`vector`, `hybrid`), фильтры по диалогу и датам. У чанков своя колонка `tsv`
с той же русской конфигурацией, что у сообщений.

Списки сливаются по **RRF** (reciprocal rank fusion): каждый чанк получает
`1/(k + позиция)` от каждого способа, баллы складываются, `k = 60`. Складывать
сами оценки нельзя — `ts_rank_cd` и косинусное расстояние живут в
несопоставимых шкалах, а ранги сравнимы всегда.

```sql
WITH vec AS (
  SELECT c.id, row_number() OVER (ORDER BY c.embedding <=> :q) AS rank
    FROM chunks c WHERE c.embedding IS NOT NULL
   ORDER BY c.embedding <=> :q LIMIT 50
), fts AS (
  SELECT c.id, row_number() OVER (ORDER BY ts_rank_cd(c.tsv, q.query) DESC) AS rank
    FROM chunks c, websearch_to_tsquery('russian', :text) q(query)
   WHERE c.tsv @@ q.query
   ORDER BY ts_rank_cd(c.tsv, q.query) DESC LIMIT 50
)
SELECT c.text,
       COALESCE(1.0/(60 + v.rank), 0) + COALESCE(1.0/(60 + f.rank), 0) AS score
  FROM vec v FULL OUTER JOIN fts f USING (id)
  JOIN chunks c ON c.id = COALESCE(v.id, f.id)
 ORDER BY score DESC LIMIT 10;
```

**На таком масштабе основной путь — точный перебор, а не HNSW.** Замер на
корпусе порядка сотни тысяч чанков: перебор 378 мс на запрос, индекс при `ef_search=1000` — 440 мс
при том же recall. Индекс с настройками послабее быстрее, но теряет соседей
(при `ef_search` 200 и 500 трудный запрос давал 6 попаданий из 10). Поэтому в
подзапросе `ORDER BY dist` идёт **по алиасу** — так планировщик выбирает
`Parallel Seq Scan`. Индекс (сотни мегабайт) оставлен на вырост: вернуться к нему —
одна правка, повторить выражение `c.embedding <=> %s` в `ORDER BY`.

**Грабли: `hnsw.ef_search` по умолчанию равен 40.** Индекс просматривает сорок
кандидатов и больше сорока строк не отдаёт, сколько ни проси в `LIMIT` —
запрос не падает, выдача просто молча обрезается.

**Грабли: оконная функция над индексным сканом ломает порядок.** Если написать
`row_number() OVER (ORDER BY embedding <=> :q)` прямо над сканом, план
становится `Limit → WindowAgg → Index Scan`, оконная функция тянет из HNSW
поток целиком, а тот отдаёт по расстоянию только первые `ef_search` кандидатов
и дальше порядок теряет. Ранги проставляются по испорченному потоку: чанк,
честно стоящий вторым по косинусу, не попадал даже в топ-20. Ранг считать
**поверх уже отобранного подзапросом**, а не поверх скана.

**Грабли: HNSW-индекс, построенный на пустой таблице.** Векторы проставлялись
через `UPDATE`, граф собирался по одной точке — recall@10 выходил 5–9 из 10.
Пересборка `DROP INDEX` + `CREATE INDEX` по готовым данным (1,5 мин,
`ef_construction=200`) поднимает его до 10 из 10. Параллельная сборка в докере
падает на нехватке `/dev/shm` — `SET max_parallel_maintenance_workers = 0`.

**Грабли: `websearch_to_tsquery` соединяет слова через AND.** Запрос
«где переночевать в другом городе» требует одновременно всех слов —
на пилоте это дало ровно один результат. Именно эту дыру и закрывает вектор.

## Пересортировка кросс-энкодером

Флаг `--rerank` в [`scripts/search.py`](../scripts/search.py), модель
`BAAI/bge-reranker-v2-m3` через [`scripts/rerank.py`](../scripts/rerank.py).

Зачем поверх готового поиска: bge-m3 кодирует запрос и чанк **по отдельности**,
вектор чанка один и тот же для всех запросов. Кросс-энкодер читает пару целиком
и отвечает на вопрос «этот кусок отвечает именно на этот запрос?». Он на два
порядка дороже, поэтому применяется не к корпусу, а к сотне кандидатов, которых
уже отобрал быстрый поиск.

Замер на 18 контрольных запросах (`eval_search.py --rerank`):

| режим | MRR | в топ-1 | в топ-5 | промахов | с/запрос |
|---|---|---|---|---|---|
| fts | 0.028 | 0 | 1 | 17 | 0,01 |
| vector | 0.423 | 6 | 9 | 6 | 0,55 |
| hybrid | 0.451 | 7 | 9 | 6 | 0,53 |
| **hybrid + реранк** | **0.592** | **9** | **12** | **4** | **4,1** |

**Применять пересортировку целиком, без страховки.** Проверены слияние ранга
кросс-энкодера с исходным рангом поиска по RRF (`k` = 60, 10, 3) и порог по
уверенности модели. Любое слияние **хуже** чистой пересортировки: 0.513, 0.522,
0.529 против 0.592 — исходный ранг разбавляет сигнал. Порог (доверять модели,
только если лучший балл выше −4) дал 0.594, то есть +0.002 на один случай —
это шум на восемнадцати запросах, а не эффект, и лишняя калибруемая ручка.

**Полнотекстовая половина после пересортировки не нужна.** `vector+rr` и
`hybrid+rr` совпали до последнего случая: кросс-энкодер сам разбирается в
лексических совпадениях. Гибрид оставлен по умолчанию, потому что стоит он
почти ничего (0,53 против 0,55 с) и страхует редкие токены и имена, которых в
контрольном наборе нет.

**Чего пересортировка не чинит.** Если цели нет в пуле — она бессильна: две
из четырёх оставшихся неудач не входят даже в топ-400, и это негодные
контрольные запросы (TD-010), а не дефект поиска.
Углублять пул смысла нет: третий промах стоит на честном ранге 61, то есть
внутри пула, и модель всё равно его не поднимает.

**Шкала балла — сырой логит, примерно от −11 до +11.** Сравнивать его можно
только внутри одного запроса: между запросами он не калиброван. Низкий балл у
первого места (ниже примерно −4) означает «в пуле не нашлось ничего толком
подходящего» — как признак сомнительной выдачи читать можно, как порог для
автоматики — нельзя, разделения не получилось.

**fp16 на MPS проверяется на NaN.** Кросс-энкодер в половинной точности может
вернуть NaN, и тогда сортировка молча станет случайной, а выдача останется
правдоподобной на вид. `rerank.py` падает сразу, а не отдаёт мусор.

## Анализ фотографий

[`scripts/analyze_photos.py`](../scripts/analyze_photos.py) → таблица
`photo_analysis`. Анализ идёт встроенным в macOS фреймворком **Vision**
(`pyobjc-framework-Vision`, +32 МБ, ничего не качается, всё на устройстве):
OCR на 30 языков, классификатор сцены на 1303 категории и детектор лиц —
за один проход по файлу.

Замер на 500 фото из личных переписок: **140 мс на картинку** при 12 потоках
скачивания (скачивание 70 мс, анализ 70 мс), текст найден в 60%, лица в 22%.
Сбоев 0,8% — мёртвые ссылки и HTML-заглушки вместо файла.

**Анализ параллелится скромно.** Vision частично распараллеливает сам: 100 мс
в один поток, 70 в четыре, восемь — не быстрее четырёх. Основной выигрыш
даёт параллельное скачивание, а не параллельный анализ.

**`accurate` против `fast`.** 70 мс против 26, но текст находится в 33 из 58
против 28 — на 18% больше картинок с текстом. Для личных переписок стоит того.

**Строка пишется и при неудаче.** Мёртвая ссылка — это факт про архив, а не
ошибка прогона: `status` = `http_error` / `html_stub` / `unreadable`. Ссылки VK
смертны (несколько десятков голосовых уже не вернуть), поэтому в таблице продублированы `url`,
`sha256`, `bytes`, `content_type` и заголовки ответа — чтобы файл можно было
опознать и достать заново, пока ссылка жива.

**Что показала сверка глазами (обязательный шаг, не пропускать):**
- OCR на скриншотах постов и переписок — **дословно точен**, включая имена,
  даты и время. Ошибается предсказуемо: на тексте, перекрытом рисунком поверх
  (обведено красным маркером → «Еда и напитки» стало «да и напитки»)
- Низкий `ocr_conf` — честный признак мусора: фото книжной страницы под углом
  дало 0.32 и кашу вместо слов. По этому полю можно фильтровать
- **Детектор лиц срабатывает на рисованных персонажах.** Аниме-мем дал два
  лица. «Фото живых людей» — это `n_faces > 0` **и** отсутствие меток
  `art` / `illustrations`, а не одно только число лиц
- Классификатор различает ровно то, что нужно: скриншот переписки →
  `document:0.96, screenshot:0.96`, арт → `art, illustrations`, селфи в лесу →
  `people, adult, snow`, макет железной дороги → `toy, diorama`
- Про 3% картинок не известно ничего: ни меток, ни текста

`tsv` на `ocr_text` построен той же русской конфигурацией, что у сообщений.
Сам по себе он поиску не помогал: `search.py` смотрит только в `chunks`.
Мост между таблицами — следующий раздел.

## Фотографии в поиске

[`scripts/build_photo_chunks.py`](../scripts/build_photo_chunks.py) заводит
осмысленной фотографии такой же чанк, как окну переписки. Не третий список
в RRF-слиянии: у чанка есть заголовок, дата, `peer_id` и эмбеддинг, поэтому
фотография сразу попадает и в полнотекстовый поиск, и в векторный, и во
второй ярус, который будет строиться поверх чанков. Отдельный список в
слиянии дал бы только первое.

Колонка `chunks.source` (`messages` | `photo`) отличает породу. Она же
входит в уникальный ключ — по двум причинам:

- у фото `part` значит другое: номер фотографии в сообщении, а не часть
  длинной реплики. Сообщение с двадцатиминутным голосовым и фотографией
  столкнулось бы ключами;
- `build_chunks.py` после нарезки удаляет из диалога чанки, которых нет в
  новой раскладке. Без фильтра `source = 'messages'` любая пересборка
  диалога стирала бы все фото-чанки вместе с посчитанными эмбеддингами.

**Порог осмысленности — три условия сразу** (`ocr_conf ≥ 0.6`, длина ≥ 40
символов, ≥ 3 слов из букв). Откалиброван по выборке: на 0.3–0.55 живут
книжная страница под углом и вывеска в перспективе — распознаётся набор
обрывков слов вперемешку с латиницей; с 0.6 начинается читаемое. Порогов по
уверенности и длине поодиночке мало — набор артикулов и номеров бывает и
длинным, и уверенным, а слов в нём нет. Примеры распознанного здесь не
приводятся намеренно: это содержимое личного архива. Порог проходят около
двух третей фотографий с распознанным текстом; отсев по словам
убирает ещё около полутора сотен.

**Метки сцены переводятся на русский** (`screenshot` → «скриншот»,
`document` → «документ») и пишутся в текст чанка: спрашивают по-русски, а
полнотекстовый поиск не знает, что это одно и то же. Незнакомая метка
остаётся английской — лучше лишнее слово, чем потерянный признак. Берём не
больше четырёх с уверенностью от 0.7: дальше идут синонимы одного и того же
(`mammal`, `feline`, `cat`, `adult_cat` на одной кошке).

**Длинный текст не режется.** Самая многословная фотография корпуса — около 7 000
символов, это укладывается в 8192 токена bge-m3. Делить пришлось бы через
`part`, где уже лежит номер фотографии.

**Номер фотографии считается по всем проанализированным фото сообщения**, а
не по прошедшим отбор: иначе смена порога сдвинула бы нумерацию и те же
фотографии легли бы в базу второй раз под новыми ключами. Отбор диалога
стоит внутри оконной функции — снаружи планировщик не проталкивает его
внутрь окна, и каждый диалог перечитывал всю таблицу: прогон по всем
занимал 39 секунд вместо 3,4.

**Уборка сносит всё, если ключей не осталось, — и это опасно.** Пустой
список значит «ни одна фотография диалога больше не проходит порог», и
старые чанки надо убрать. Но ровно так же выглядит дефект в самом запросе,
только тогда ноль вернётся для всех диалогов подряд и прогон молча снесёт
весь слой вместе с эмбеддингами. Поэтому перед сносом тот же вопрос
задаётся независимой формулировкой — без CTE и окна, но с теми же порогами
(пороги повторить обязательно: их поднимают руками, и тогда ноль — честный
ответ). Расхождение ответов останавливает прогон. Проверено обеими
ветками: подменённый запрос ловится и чанки остаются на месте, поднятый
порог убирает старое как задумано.

**`CHECK (source IN ('messages','photo'))` ставится и миграцией.** В
`db/schema.sql` он был, а `ensure_schema` его не ставил — на томе, где
колонка появилась миграцией, ограничения не оказалось. Без него опечатка
(`photos`, `Photo`) заводит третью породу строк: её не отбирает ни один
фильтр по `source`, не убирает ни одна из двух уборок, а в поиск по
умолчанию она попадает.

Замер после наполнения: корпус порядка **125 тысяч чанков**, из них седьмая
часть — с фотографий; эмбеддинги считаются со скоростью 13,8 чанк/с
(фото-чанки короткие, 394 символа против 1200 у переписки).

**Чем это оплачено — и чем нет.** На восемнадцати разговорных запросах
фотографии вытесняют переписку из выдачи: гибрид **0.451 → 0.402**, первых
мест 7 → 6, промахов 6 → 7. Проверено, что это именно вытеснение, а не
поломка: `eval_search.py --source messages` воспроизводит корпус без фото и
даёт ровно прежние числа. **Пересортировка кросс-энкодером потерю снимает
целиком: 0.592 против 0.592** — модель сама отправляет вниз картинки,
попавшие в пул не по делу.

Обратная сторона мерится отдельным набором (`--photo-cases`, шесть случаев,
ответ на каждый есть только на фотографии): **0.083 → 0.875**, промахов
5 из 6 → 0. Цели в нём выбраны так, чтобы за сутки вокруг них в диалоге не
было других фотографий, — иначе допуск в сутки засчитал бы соседнюю.
Полнотекстовый поиск на этом наборе даёт ноль: запросы там по смыслу, а
`websearch_to_tsquery` требует все слова разом.

Флаг `--source` в `search.py` ограничивает выдачу одной породой: полезно
посмотреть, что вообще нашлось на картинках, или наоборот убрать их.

## Порядок наполнения

1. `docker compose up` → schema.sql применится сам при первом старте
2. Импорт `dialogs` (index + participation.json) — скрипт `db_import.py`
3. Фаза 1: парсер messages/attachments (батчами по диалогу, idempotent upsert
   по `(peer_id, vk_msg_id)`)
4. Импорт имеющихся transcription-артефактов (batches → prompt_batches,
   meta.json → voice_transcripts, vocab → vocab_terms, periods → dialog_periods)
5. Фаза 3: чанкер + эмбеддинги → chunks
6. Анализ фотографий (`analyze_photos.py`) → фото-чанки
   (`build_photo_chunks.py`) → те же эмбеддинги (`embed_chunks.py --all`)

## Решённые по ходу вопросы

- Модель эмбеддингов: выбрана **bge-m3** локально через Ollama; пилот и
  замеры качества — в README и PLAN.md
- Таймзона `sent_at`: экспорт даёт МСК без смещения — храним как
  `timestamptz` в Europe/Moscow, допущение зафиксировано в `db_import.py`
